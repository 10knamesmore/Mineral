# 持久化开发

业务数据库统一通过 SeaORM 访问：`mineral-persist` 管理服务状态、客户端状态和文件缓存索引，`mineral-stats` 管理播放事实、事件与统计聚合。数据库连接与事务使用 SeaORM API，SQLite 驱动由 SeaORM 内部提供。

## 实体与查询

两个 crate 的 `src/entity/` 保存实体模型。表名在实体上声明，列标识和写入模型由字段派生；普通读写使用实体查询和具名字段赋值。批量元数据写入保持分块与整批事务，避免退回逐首事务。

聚合、窗口函数和跨事件表清理使用 SeaORM 提供的结构化表达式。持久化字段始终引用实体列；聚合结果的别名使用独立的列枚举。歌曲身份按来源和裸值共同关联，歌单条目保留原始位置及歌曲自身来源。

## Rust migration

迁移位于各 crate 的 `src/migration/`，由 `registry.rs` 注册顺序，每个版本实现 `up` 和 `down`。建表、删表、索引、外键与 CHECK 约束均通过 Rust 结构化 API 表达，不嵌入 SQL 文件。打开数据库时自动执行尚未应用的版本；正常编译不需要开发数据库或离线 SQL 元数据。

初始版本的 `server_schema/`、`client_schema/`、`stats_schema/` 是独立的结构快照，不引用当前实体定义。后续修改实体时，新增一个迁移版本并注册，明确写出结构变化与回滚方式，避免实体变化反过来改变历史迁移。事件表新增后还须进入事件表集合，确保统计、保留期清理和会话引用判断都覆盖它。

这次预发布切换将原 SQL 迁移链归并为当前结构的 Rust 基线，使用 SeaORM 迁移账本。旧预发布数据库需要重建；迁移不会自动接管旧账本或删除用户数据库。

## 验证

现有业务测试覆盖元数据富化、来源隔离、重复条目、收藏排序、会话和客户端状态、事件枚举、报表口径以及保留期清理。迁移测试覆盖重复执行、完整 `up → down → up` 和数据库约束。数据库测试使用独立临时目录或单连接内存库。

修改完成后运行全仓 release 测试、doctest 和严格 lint：

```bash
cargo t
cargo td
cargo clippy --workspace --all-targets --release -- -D warnings
cargo fmt --all -- --check
```
